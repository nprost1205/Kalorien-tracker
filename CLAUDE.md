# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Kalorien- und Nährstoff-Tracker als rein statische Web-App (UI komplett auf Deutsch). Kein Build, keine Abhängigkeiten, kein Server: Der Nutzer öffnet `index.html` per Doppelklick in Edge/Chrome (`file://`). Auf dem Rechner sind weder Node.js noch Python installiert.

## Deployment (Handy)

- The user also runs the app on an **Android phone** as an installable PWA hosted on **GitHub Pages** (user-owned account; git is not installed, files are uploaded via the GitHub web UI, served under `https://<user>.github.io/kalorien-tracker/`). There is no sync: each device keeps its own localStorage, data moves via the backup export/import (on the phone also via "Backup teilen", which uses the Web Share API with a `.txt` file because Chrome doesn't allow sharing `.json`).
- PWA files: `manifest.webmanifest`, `sw.js`, `icons/`. The manifest `<link>` is injected and the service worker registered **only over http(s)**, so `file://` on the PC keeps working without console errors. All paths are relative (the app lives in a subpath on Pages).
- `sw.js` is network-first (3 s timeout, `cache: 'no-cache'`) with cache fallback, same-origin GET only. **When adding/renaming app files, update `ASSETS` and bump `CACHE`** (`kalorien-tracker-vN`). After any change the user must re-upload the changed files to GitHub.

## Running / testing

- Run: open `index.html` in the browser. There are no build, lint, or test commands.
- The Claude browser pane renders `file://` pages only as static snapshots (no CSS/JS), so serve the folder over HTTP for testing, e.g. a PowerShell `System.Net.HttpListener` script started via `.claude/launch.json` (no Python/Node available). Remember that `localhost` has its own localStorage, separate from the user's `file://` data. To test the PWA like on Pages, serve the folder under `/kalorien-tracker/`; afterwards unregister the service workers and delete the caches in the test browser so later tests aren't served stale files.

## Constraints

- `app.js` must stay a classic `<script>`: ES modules and `fetch` of local files are blocked under `file://`.
- No external libraries/CDNs; everything except the product search must work offline (the chart is hand-built SVG).
- Only Open Food Facts is contacted over the network. It sends `Access-Control-Allow-Origin: *`, which is why requests from origin `null` work. Search is triggered only by button/Enter, never while typing (OFF rate limit ≈10 searches/min).

## Architecture (`app.js`)

- `NUTRIENTS` is the single source for nutrient keys, labels, units, decimals, `kind` (`max` = limit, shown red when exceeded; `min` = target, ✓ when reached) and the OFF field name. Goal forms and manual-entry inputs are generated from it, so a new nutrient only needs to be added there (plus `DEFAULT_GOALS`). Tracked nutrients: kcal, protein, carbs, fat, fiber. Sugar and salt were removed completely at the user's request; `normalizePer100()` / `normalizeState()` drop their values from older data and backups.
- State lives in localStorage under `kalorienTracker.v1`: `{ version, goals, foods, recipes, diary, activities }`. `recipes`, `recipe.instructions` and `activities` were added later without a version bump; `normalizeState()` fills defaults for older data/backups (and drops unknown keys, e.g. an `ai` object left over from a removed AI feature), so new fields must be added there. `diary` is keyed by local-date strings `YYYY-MM-DD` (built with `dateKey()`, never `toISOString`, to avoid time-zone shifts).
- Sport: `activities` is keyed by date like `diary` (`[{ id, name, kcal }]`). Burned kcal (`burnedKcal(key)`) raise the kcal goal of that day by the full amount **and the carb goal by 1 g per 4 kcal** (`SPORT_KCAL_PER_G_CARBS`, user's request); other macros stay unchanged. Always go through `dayGoals(key)` / `sportBonus(burned)`: the day summary, history averages (`avgGoals`) and `todaysRest()` use them; the history chart and bar colors use the kcal goal incl. sport. Days count as "logged" for averages only if they have food entries.
- Fueling (food/drinks during sport): normal diary entries with `meal: 'fueling'` (last entry in `MEALS`, so it's in the dialog's meal select and counts in all totals). It is **not** rendered in `#meals` but inside the sport card (`renderFueling`), visible once the day has an activity or fueling entries. `bindDayEvents` binds the add/delete/grams handlers to both `#meals` and `#sport`.
- Diary entries store a **copy** of `per100` nutrient values, so they stay correct when a product is removed from `foods` (which only feeds the "Zuletzt verwendet" list).
- Recipes (`{ id, name, servings, totalWeight|null, ingredients[] }`) store ingredients in the same item shape as diary entries (`normalizeItem()`, rendered by `itemRow()`). `recipeStats()` derives totals, per-serving and per-100 g values (per 100 g uses `totalWeight` if set, else the ingredient sum). `recipeAsFood()` turns a recipe into a food object (`isRecipe: true`, `servingG` = one portion) so the add dialog handles it like a product. Logging a recipe snapshots its current `per100`, so later recipe edits don't change past days. Recipes are not added to `foods`.
- The add dialog serves two targets (`dialogTarget`): `'diary'` logs an entry, `'recipe'` appends an ingredient to `recipeDraft` (the in-memory working copy of the recipe editor, only persisted on "Rezept speichern"). Open it via `openDialog({ target, title, meal, food })`.
- In the recipe editor, ✎ opens an inline form to edit an ingredient's name and per-100 g values (`ingredientEditor()` / `applyIngredientEdit()`), and `nutrientsPlausible()` marks ingredients (⚠) whose kcal don't match the macros. Enter inside ingredient inputs is intercepted so it doesn't submit (save) the whole recipe form.
- AI recipes use **Google Gemini** directly from the browser (user's choice; an earlier local-Ollama version was removed because setup was too complicated — keep setup to "paste one API key"). Section „KI-Rezepte“ in `app.js`: the key (`kalorienTracker.geminiKey`) and model (`kalorienTracker.geminiModel`) live in their own localStorage keys, **outside `state`, so they never end up in backups**. `geminiFetch()` (header `x-goog-api-key`, timeout, cancel) → `models/{model}:generateContent` with `systemInstruction` + `responseMimeType: 'application/json'` + `responseSchema: AI_SCHEMA` (German field names via `AI_FIELDS`). The model is picked from `models.list` (`geminiListModels()`: stable `gemini-X-flash`, lite ranked last; fallback `AI_FALLBACK_MODEL`), a 404 clears the stored model. `geminiText()` skips `thought` parts. `parseAiRecipe()` → recipe editor with `draftFromAi` (note, ingredient brand `AI_BRAND` until edited; discarding returns to the AI card). Only the wish text and optionally today's remaining budget (`todaysRest()`, incl. sport) are sent. Verified from the browser that the real API answers CORS requests (invalid key → 400 `API_KEY_INVALID`); successful responses were only tested with a mocked `fetch`.
- "Rezept aus Video-Text" (no AI, user's choice; videos come from TikTok/Instagram, which can't be fetched from the browser): the user pastes a copied caption. `parseRecipeText()` splits it into title, servings, `sourceUrl`, ingredients and steps (headers like „Zutaten“/„Zubereitung“ optional; emojis, hashtags, bullets stripped by `cleanLine()`); `parseIngredientLine()` converts amounts via `UNITS` / `PIECE_WEIGHTS` to grams and flags approximations as estimated. Ingredients get nutrients from a matching saved product (`matchSavedFood()`), otherwise `per100` is all `null` — such draft ingredients show „Nährwerte suchen“ (dialog target `'ingredient'` replaces that ingredient's values, keeping its grams) and the recipe can't be saved until every ingredient has kcal. Import-only hints live in `draftImport` (not persisted). Recipes have an optional `sourceUrl` (http(s) only), shown as „▶ Video ansehen“.
- Einkaufsliste (view `shopping`): `state.shopping` is an array of `{ id, name, grams|null, sources[], checked }` (added later; `normalizeState()` defaults it to `[]`). Manually typed items keep the text as entered (`grams: null`); recipe ingredients are added via „🛒 Einkaufen“ in the recipe list (`shopRecipeId` = row with the inline portions form) → `addRecipeToShopping()` scales grams by portions/servings and can skip `SPICES` / `PANTRY_BASICS`. `addShoppingItem()` merges with an **unchecked** item of the same name (case-insensitive) by summing grams; checked items are never merged. „Liste teilen“ uses the Web Share API, falling back to the clipboard.
- Märkte (user chose: sort the list by store, no stock/price data — none freely exists): `state.shops` `[{ id, name, detail, osm }]`, `state.shopAssignments` `{ shoppingKey → shopId }` (remembered per ingredient; `shoppingKey()` strips amounts so „2 Eier“ and „Eier“ match), `state.shopLocation` `{ label, lat, lon }` (saved address), and `shopId` on shopping items. With any open item assigned, `renderShopping()` groups by store (`shoppingGroups()`); share text is grouped too. The picker dialog (`#shopPicker`, `openShopPicker()`) offers saved stores, a nearby search and a free-text store. Nearby search uses **Nominatim** only (`searchNearbyShops()`: one bounded `viewbox` query per type in `NEARBY_QUERIES`, sequential with `NOMINATIM_GAP_MS` ≥ 1 s per the usage policy, filtered by `category/type`, deduped, sorted by distance, 3 km). Overpass was tried first but returned 504s/timeouts at build time — don't switch back without re-testing. GPS position (`currentPosition()`) is used for one search and not stored; the address is. Results are cached in memory (`nearby`) for the session. The GPS button was not tested in a real browser.
- Vorrat (user chose: only missing ingredients go on the list): `state.pantry` `[{ id, name }]`, managed in the Einkauf tab (comma-separated input) and via „📦 hab ich“ in the recipe's „🛒 Einkaufen“ form. `shopAddForm()` lists every ingredient with a checkbox; `shopSkipReason()` pre-unchecks pantry matches, water (`WATER_PATTERN`) and `SPICES`. User overrides live in `shopChecks` and portions in `shopPortions` (kept across re-renders); portions/checkbox changes update the form in place. `pantryMatches()` compares `shoppingKey()`s: same word incl. simple plural forms (`wordForms()`), multi-word sequences, or compound word endings („Öl“ → „Olivenöl“; short entries only match their base form so „Ei“ doesn't match „Rotwein“). `addRecipeToShopping(recipe, portions, selectedIndexSet)`.
- Recipe properties: `recipe.tags` ⊆ `RECIPE_TAGS` keys (`vegan`, `vegetarian`, `lowcal`, `highcarb`, `highprotein`; limits per portion `LOWCAL_MAX_KCAL` 500, `HIGHCARB_MIN_G` 60, `HIGHPROTEIN_MIN_G` 30. The user wants „kohlenhydratreich“, not low-carb), defined in the config block at the top of `app.js` (must stay there: `normalizeState()` runs at load, before later `const`s are initialized). `normalizeTags()` keeps order and makes vegan imply vegetarian; `toggleTag()` removes vegan when vegetarian is unset. Chips appear in the AI card (selection persisted in localStorage key `kalorienTracker.aiTags`, sent as hard requirements via `buildAiUserPrompt()` and copied onto the generated recipe), in the recipe editor, as badges in the recipe list, and as an AND filter (`recipeFilterTags`, session only). `tagWarnings()` checks per-portion limits (`LOWCAL_MAX_KCAL`, `HIGHPROTEIN_MIN_G`, only when all ingredients have kcal), flags obviously non-vegan/vegetarian ingredient names via `MEAT_FISH_PATTERN` / `ANIMAL_PATTERN` (skipping `PLANT_BASED_PATTERN`), and suggests lowcal/highprotein when the numbers qualify. Tags are never set automatically.
- „Mag ich nicht“: `state.dislikes` `[{ id, name }]` (card `#dislikeCard` in the Rezepte view, hidden while the editor is open). Used in `buildAiUserPrompt()` (always sent as "never use"), as 👎 badges in the recipe list plus a „👎 ausblenden“ filter chip (`hideDisliked`, session only), and as a note in the editor (`recipeDislikes()`). `pantry` and `dislikes` share `normalizeNameList()` and the matcher `nameMatches()`: `INGREDIENT_GROUPS` maps umbrella terms (Pilze, Fisch, Meeresfrüchte, Nüsse, Innereien) to concrete ingredients; dislikes additionally match compound **prefixes** incl. singular stem (`{ prefix: true }`: „Fisch“ → „Fischsauce“, „Pilze“ → „Pilzfond“), the pantry deliberately does not („Tomaten“ must not mark „Tomatenmark“ as in stock). `wordForms()` only allows „-er“ for words shorter than 3 letters („Ei“ → „Eier“, not „Eis“).
- ✨ Ersetzen / Rausnehmen (only in AI drafts, `draftFromAi` + stored key): per ingredient `data-ing-ai` opens `aiSwapPanel()`; state `swap` `{ ingredientId, wish, status, isError, abort }`. `runIngredientSwap(mode)` sends the whole draft (grams, steps, tags, dislikes) via `buildSwapPrompt()` with `AI_SWAP_PROMPT` / `AI_SWAP_SCHEMA` (`name`, `ersatz[]`, `zubereitung[]`, `hinweis`). Only the target ingredient is spliced out/replaced (`parseAiIngredients()`, shared with `parseAiRecipe()`), instructions and name are overwritten; all other ingredients and user edits stay. `swapResult` keeps a one-level undo snapshot („↩ Rückgängig“ in `#recipeNote`). Saving is blocked while a swap runs; deleting the target ingredient or closing/switching the editor aborts it.
- Kochansicht (`#cookDialog`, „👩‍🍳 Kochen“ in the recipe list): `openCookView()` / `renderCook()`; session-only state `cook` `{ recipeId, portions, checked, done }` is kept when the same recipe is reopened. Ingredient amounts scale with portions (`fmtShopGrams`), steps come from `instructionSteps()`, the first undone step is `.current`. `stepTimers()` parses „10 Minuten“, „5-7 Min.“ (upper bound), „1 Stunde“, „30 Sek.“ into timer buttons; `cookTimers` tick via `tickCookTimers()`, which only updates the time text in place (full re-render would swallow clicks) and survive closing the dialog (toast when finished, otherwise the timer blinks red). Sound, vibration and Screen Wake Lock were built and then removed at the user's request — don't re-add them unasked. No backdrop-click close on purpose.
- Recipe list tools (`#recipeTools`): search in name + ingredient names (`recipeMatchesSearch()`, all words must match), sort (`sortRecipes()` by name or per-portion kcal/protein/carbs), view toggle „Karten“/„Übersicht“ (persisted per device in localStorage `kalorienTracker.recipeView`; the table from `recipeTable()` opens the Kochansicht on row tap/Enter). Sharing is **per recipe only** (user doesn't want to share the whole list): 📤 in each recipe card and „📤 Teilen“ in the Kochansicht call `shareRecipe()` → `recipeText()` (Web Share API, clipboard fallback). Search/sort are session-only; the search input is static markup so it keeps focus while `renderRecipes()` re-renders.
- **Element IDs must be unique across `index.html`** (dialogs included): a duplicate `#recipeFilter` once silently broke „Eintragen“ for recipes because `$()` returned the wrong element. Check for duplicates after adding markup.
- The header nav now has 6 tabs; on narrow screens they are spaced to fit 375 px and scroll horizontally as a fallback.
- Nutrient values may be `null` (unknown, shown as "–", counted as 0); `kcal` is always required.
- `normalizeState()` validates and cleans both localStorage data on load and imported backups. Corrupt stored data is copied to `kalorienTracker.v1.defekt-<timestamp>` instead of being overwritten.
- All totals go through `calcNutrients()` / `sumEntries()` (day view, dialog preview, history).
- Rendering uses template strings + `innerHTML`; always pass user/OFF text through `esc()`.
- Views (`day`, `history`, `recipes`, `goals`, `data`) are `<section id="view-…">` toggled by `showView()`, which calls the matching function in `RENDERERS`. Changes from another tab arrive via the `storage` event.
